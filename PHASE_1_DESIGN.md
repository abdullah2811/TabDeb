# Phase 1: Speech Pipeline - Data & API Contract Design

## Overview
Phase 1 establishes the complete data model, Firestore schema, Firebase Storage conventions, backend API contract, and client-side polling strategy for the speech transcription and summarization pipeline. This foundation enables Phase 2 (backend) and Phase 3 (Flutter integration) to proceed in parallel without blocking.

---

## 1. Data Model: SpeechJob

**File**: `lib/models/speech_job.dart`

### Job Lifecycle States
Every job transitions through these states exactly once (except on failure):

```
uploaded → transcribing → transcribed → summarizing → completed
                ↓              ↓               ↓              ↓
              failed         failed         failed         (SUCCESS)
```

**State Definitions**:
- **uploaded**: Audio file received by backend; queued for transcription
- **transcribing**: Whisper API is processing audio
- **transcribed**: Transcript text available; awaiting user to click "AI Summarize"
- **summarizing**: Groq API is generating summary from transcript
- **completed**: Both transcript and summary available; no further processing
- **failed**: Unrecoverable error occurred; see `error` field for details

### Core Fields
```dart
class SpeechJob {
  // Identity & ownership
  final String id;           // UUID generated by backend
  final String userId;       // Firebase UID (derived server-side from token)
  final String? tournamentId;// Optional tournament context

  // State tracking
  SpeechJobStatus status;    // Current lifecycle state
  DateTime createdAt;        // When uploaded
  DateTime? updatedAt;       // Last state change
  DateTime? completedAt;     // When reached terminal state

  // Processing results
  String? transcript;        // Available when status >= transcribed
  String? summary;           // Available when status == completed
  String? error;             // Error message if status == failed

  // Metadata
  final int? durationSeconds;      // Original audio duration
  final String? audioStoragePath;  // Path in Firebase Storage
}
```

### Helper Methods
- `toJson()` / `fromJson()` — Firestore serialization
- `copyWith()` — Immutable field updates
- `isProcessing` — True if transcribing or summarizing
- `isFinished` — True if completed or failed
- `statusLabel` — Human-readable status for UI

## 2. Firestore Schema

**File**: `lib/constants/storage_constants.dart`

### Collections & Document Structure

#### Primary Index: `speech_jobs/{jobId}`
```
Collection: speech_jobs
├─ Document: {jobId}
│  ├─ id: string (UUID)
│  ├─ userId: string (Firebase UID)
│  ├─ tournamentId: string? (optional)
│  ├─ status: string (enum: uploaded|transcribing|transcribed|summarizing|completed|failed)
│  ├─ durationSeconds: number?
│  ├─ transcript: string? (null until transcribed)
│  ├─ summary: string? (null until completed)
│  ├─ error: string? (error message if failed)
│  ├─ audioStoragePath: string (gs:// reference)
│  ├─ createdAt: timestamp
│  ├─ updatedAt: timestamp?
│  └─ completedAt: timestamp? (present when status is terminal)
```

**Purpose**: Enables admin dashboards, analytics, and bulk job monitoring

#### User Index: `users/{uid}/speech_jobs/{jobId}`
```
Collection: users/{uid}
└─ Subcollection: speech_jobs
   └─ Document: {jobId}
      [Same schema as primary index]
```

**Purpose**: Fast user-specific queries (e.g., "load my recent jobs") without cross-user leakage

#### Optional Metadata: `users/{uid}/speech_metadata/{jobId}`
```
Collection: users/{uid}
└─ Subcollection: speech_metadata
   └─ Document: {jobId}
      ├─ transcriptWordCount: number
      ├─ summaryWordCount: number
      ├─ processingDurationSeconds: number
      └─ [Other analytics]
```

**Purpose**: Denormalized stats for fast UI rendering without parsing large transcript/summary

### Firestore Indexes (Required)
Create these composite indexes for efficient queries:

1. **Collection**: `speech_jobs`
   - **Fields**: `userId` (Asc), `createdAt` (Desc)
   - **Use Case**: "Get all jobs by user, sorted by newest"

2. **Collection**: `speech_jobs`
   - **Fields**: `status` (Asc), `updatedAt` (Desc)
   - **Use Case**: "Find all active jobs for backend workers" or "Get failed jobs for retry"

3. **Subcollection**: `users/{uid}/speech_jobs`
   - **Fields**: `status` (Asc), `createdAt` (Desc)
   - **Use Case**: "Load user's active jobs" for dashboard

## 3. Firebase Storage Schema

**File**: `lib/constants/storage_constants.dart`

### Storage Paths & Naming Convention

#### Audio Files
```
gs://bucket/speech_audio/{uid}/{jobId}.m4a
  ├─ {uid}:      Firebase User ID (UUID format)
  ├─ {jobId}:    Job identifier (UUID format, same as Firestore doc ID)
  └─ {format}:   Always .m4a (AAC-LC codec from Flutter record package)
```

**Example**: `gs://bucket/speech_audio/user_abc123/job_xyz789.m4a`

#### Generated Reports (Future)
```
gs://bucket/speech_reports/{uid}/{jobId}.pdf
  └─ [Same path structure as audio]
```

**Example**: `gs://bucket/speech_reports/user_abc123/job_xyz789.pdf`

### Access Control
- **Audio files**: Private until deleted; only user and backend service account can read
- **Reports (if server-generated)**: Private; only user can download
- **Delete policy**: Optional; configurable per deployment
  - Option A: Keep audio indefinitely (audit/compliance)
  - Option B: Delete after 30 days (privacy/cost)
  - Option C: User selectable (future UI enhancement)

### Helper Functions
```dart
// Construct path to user's audio file
StorageConstants.audioFilePath(uid, jobId)
// → "speech_audio/user_abc123/job_xyz789.m4a"

// Extract job ID from audio path
StorageConstants.extractJobIdFromAudioPath(path)
// → "job_xyz789"
```

## 4. Backend API Contract

**File**: `lib/constants/api_contract.dart`

### Base Configuration
```
Base URL: https://api.example.com/v1
Auth: Bearer {firebaseIdToken} in Authorization header
Version: v1 (in path prefix)
```

### Endpoints Summary

| Method | Endpoint | Purpose | Auth Required |
|--------|----------|---------|---|
| POST | `/speech-jobs` | Create job + get upload URL | Yes (token) |
| GET | `/speech-jobs/{jobId}` | Poll job status | Yes (token) |
| POST | `/speech-jobs/{jobId}/summarize` | Trigger summarization | Yes (token) |

### Endpoint Details

#### 1. Create Speech Job
```
POST /v1/speech-jobs
Authorization: Bearer {firebaseIdToken}

Request Body:
{
  "audioFileSize": 2048576,        // bytes (validated server-side)
  "durationSeconds": 120,          // optional, seconds
  "tournamentId": "tourn_abc123"   // optional, tournament UUID
}

Response (201 Created):
{
  "jobId": "job_xyz789",
  "status": "uploaded",
  "uploadUrl": "https://storage.googleapis.com/bucket/...?signature=...",
  "audioStoragePath": "speech_audio/user_abc123/job_xyz789.m4a",
  "createdAt": "2025-04-05T14:30:00Z",
  "expiresIn": 3600             // seconds until URL expires
}
```

**Next Steps**:
1. Upload audio to `uploadUrl` via `PUT {uploadUrl}` with Content-Type: audio/m4a
2. Poll `/speech-jobs/{jobId}` to track transcription progress
3. When status becomes "transcribed", user can click "AI Summarize"

#### 2. Get Job Status (Poll)
```
GET /v1/speech-jobs/{jobId}
Authorization: Bearer {firebaseIdToken}

Response (200 OK):
{
  "jobId": "job_xyz789",
  "status": "transcribing",       // One of: uploaded|transcribing|transcribed|summarizing|completed|failed
  "userId": "user_abc123",
  "durationSeconds": 120,
  "transcript": null,              // null until transcribed
  "summary": null,                 // null until completed
  "error": null,                   // error message if failed
  "createdAt": "2025-04-05T14:30:00Z",
  "updatedAt": "2025-04-05T14:31:15Z",
  "completedAt": null              // present when status is terminal
}
```

**Status Progression Examples**:
- After 30 seconds: `status: "transcribing"`
- After 2 minutes: `status: "transcribed", transcript: "Today I want to discuss..."`
- On user click "Summarize": `status: "summarizing"`
- After 1 minute: `status: "completed", summary: "Speaker argues that X is important because Y."`

#### 3. Trigger Summarization
```
POST /v1/speech-jobs/{jobId}/summarize
Authorization: Bearer {firebaseIdToken}

Request Body (optional):
{
  "settings": {
    "maxLength": 500  // optional, default 200 characters
  }
}

Response (202 Accepted):
{
  "jobId": "job_xyz789",
  "status": "summarizing",
  "message": "Summarization started"
}
```

**Immediately After**:
- Job status transitions to "summarizing"
- User is shown loading indicator
- Frontend polls `/speech-jobs/{jobId}` every 5 seconds
- When status becomes "completed", summary text is displayed

### Error Response Format
```
{
  "error": "invalid_state",        // Error code (see below)
  "message": "Cannot summarize job in status 'uploaded'; must be 'transcribed'",
  "statusCode": 409,
  "timestamp": "2025-04-05T14:30:00Z"
}
```

**Error Codes**:
- `invalid_token` (401): Firebase token expired or invalid → suggest re-login
- `forbidden` (403): User doesn't own this job → prevent cross-user access
- `job_not_found` (404): Job ID doesn't exist → show "Job not found" error
- `invalid_state` (409): State transition not allowed (e.g., summarize before transcribe) → explain requirement to user
- `invalid_request` (400): Bad parameters (e.g., audioFileSize too large) → validation error
- `internal_error` (500): Backend failure → user-friendly message + retry option

## 5. Client-Side Polling Strategy

**File**: `lib/constants/polling_config.dart`

### Polling Intervals

| State | Interval | Reason |
|-------|----------|--------|
| `uploaded` | 2 seconds | Rapid feedback after upload |
| `transcribing` | 5 seconds | Active job; user is waiting |
| `transcribed` | None | User action required; no polling |
| `summarizing` | 5 seconds | Active job; user is waiting |
| `completed` / `failed` | None | Terminal; stop polling |

### Timeout Budgets

- **Transcription**: 15 minutes (covers up to ~25-minute debate speech + backend processing)
- **Summarization**: 2 minutes (Groq is typically fast)
- **Max Job Lifetime**: 20 minutes (safety net for entire lifecycle)

### Automatic Retry Strategy

**Exponential Backoff** (when enabled):
- Attempt 1: 1s
- Attempt 2: 2s
- Attempt 3: 4s
- Attempt 4: 8s
- Attempt 5+: 30s (capped)

**Retryable HTTP Status Codes**:
- 408 (Request Timeout)
- 429 (Too Many Requests)
- 500-504 (Server errors)

### Manual Retry
- User can tap "Retry" button up to 3 times if polling times out
- Each retry resets the attempt counter and timeout budget
- After 3 manual retries, show "Contact Support" message

### Example Polling Lifecycle
```
1. User stops recording (2 min debate speech)
   → Job created with status: uploaded

2. Poll #1 (2s): status = uploaded
3. Poll #2 (2s): status = transcribing        ← Transcription starts
4. Poll #3-#20 (5s each): status = transcribing
5. Poll #21 (5s): status = transcribed, transcript = "..." ← Show transcript UI

6. User clicks "AI Summarize"
   → Backend job state: summarizing

7. Poll #1 (5s): status = summarizing
8. Poll #2-#5 (5s each): status = summarizing
9. Poll #6 (5s): status = completed, summary = "..." ← Show summary UI

Total time: ~2 min recording + ~2 min transcription + ~30 sec summarization = ~4.5 min
```

### PollingTracker Class
Helper class to track polling state and determine when to stop:
```dart
class PollingTracker {
  int transcriptionAttempts = 0;
  int summarizationAttempts = 0;
  int manualRetries = 0;

  bool shouldContinueTranscriptionPolling() { ... }
  bool shouldContinueSummarizationPolling() { ... }
  void resetForManualRetry() { ... }
  bool canRetryManually() { ... }
  int remainingManualRetries() { ... }
}
```

## 7. Design Principles & Rationale

### Why Async Jobs + Polling?
- ✅ **Scalability**: Backend can process jobs at its own pace without holding HTTP connections
- ✅ **Resilience**: Client/server can disconnect; job continues; client resumes polling
- ✅ **Fault Isolation**: One hung job doesn't block other users
- ⚠️ **Trade-off**: User sees "loading" state; no real-time WebSocket updates yet

### Why Separate Transcript & Summary?
- ✅ **User Control**: User can read transcript before deciding to summarize
- ✅ **Cost Saving**: Summarization costs money (Groq API); user chooses when to incur it
- ✅ **Flexibility**: Future: allow re-summarizing with different settings

### Why Firestore Indexes?
- Enables queries like "Get all transcription jobs for admin dashboard"
- Enables "Show user's job history, sorted by newest"
- Prevents full-collection scans and `O(n)` query costs

### Why Max Timeout Budgets?
- ⏱️ **UX**: Users don't wait indefinitely; clear failure after 15 min
- 💰 **Cost**: Long-running jobs use bandwidth/compute; budget prevents resource waste
- 🔄 **Retry**: User knows exactly when and how to retry

## 9. Data Flow Diagram

```
User Records Speech
    ↓
(1) SummarizerScreen calls: BackendService.createJob(audioFileSize)
    ↓
(2) Backend creates FirestoreDocument(firestore: speech_jobs/{jobId}, status: uploaded)
    ↓
(3) Backend returns: CreateSpeechJobResponse(uploadUrl, expiresIn)
    ↓
(4) Flutter uploads audio to uploadUrl → Firebase Storage
    ↓
(5) Flutter starts polling: BackendService.getJobStatus(jobId)
    ↓
(6) Backend workers:
    - Detect audio in Storage
    - Run Whisper transcription
    - Update Firestore: status: transcribed, transcript: "..."
    ↓
(7) Flutter receives: status: transcribed, transcript: "..."
    - UI shows transcript text
    - Enable "AI Summarize" button
    ↓
(8) User clicks "AI Summarize"
    - Flutter calls: BackendService.summarize(jobId)
    ↓
(9) Backend:
    - Detects summarization request
    - Run Groq summarization on transcript
    - Update Firestore: status: completed, summary: "..."
    ↓
(10) Flutter receives: status: completed, summary: "..."
     - UI shows both transcript and summary
     - Enable "Export PDF" and "Close" buttons
    ↓
End: User can export PDF or close screen
```

## 10. Security Considerations

### ✅ Implemented at Design Phase
- **Token-based auth**: Every API request validated via Firebase ID token
- **User ownership**: Backend derives `userId` from token; can't access other users' jobs
- **API key secrecy**: OpenAI and Groq keys **never** leak to Flutter; only on backend
- **Storage isolation**: User audio isolated in separate Storage folder; signed URLs time-limit access

### ⚠️ To Implement in Phase 2
- **Rate limiting**: Prevent user from creating 1000 jobs per second
- **File validation**: Verify audio format, duration, and size limits
- **Encryption at rest**: Store sensitive audit logs encrypted
- **Secrets management**: Use environment variables or Secret Manager, never hardcoded

## 11. Configuration & Environment

### Flutter (Client-side)
- **Required**: Backend base URL (e.g., `https://api.example.com`)
- **Never store**: OpenAI/Groq API keys in Flutter
- **Platform-specific**: Microphone + network permissions in AndroidManifest / iOS Info.plist

### Backend (Python)
- **Required environment variables**:
  ```
  OPENAI_API_KEY=sk-proj-xxxxx      (for Whisper)
  GROQ_API_KEY=gsk-xxxxx             (for Groq)
  FIREBASE_CREDENTIALS=...           (for Firestore + Storage auth)
  FIREBASE_BUCKET=project-bucket     (Firebase Storage bucket name)
  ```
- **Never commit**: `.env` files or hardcoded secrets
