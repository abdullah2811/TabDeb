ABSTRACT
------------------------------------------------------------
TabDeb is a cross-platform debate tournament management system developed to replace manual and error-prone tournament handling methods with a digital, integrated, and automated workflow. The application supports account management, tournament creation, team registration, round configuration, matchup generation, score submission, standings calculation, reporting, time keeping, and AI-assisted speech processing. It was designed for debate organizers, tab directors, adjudicators, and participants who need a reliable and structured way to manage tournament operations.

The system is implemented using Flutter and Dart for the client application, Firebase Authentication and Cloud Firestore for secure user and data management, and Firebase Hosting for web deployment. In addition, the speech workflow integrates recording, transcription, summarization, and PDF export so that debate speeches can be documented more efficiently. The final result is a practical platform that reduces manual work, improves fairness, and preserves tournament data in a structured and reusable form.

1. INTRODUCTION
------------------------------------------------------------
Debate tournaments require careful coordination of participants, rounds, scores, room assignments, rankings, and official records. In traditional practice, much of this work is handled manually through spreadsheets, paper records, or fragmented digital files. As the number of teams and rounds increases, the likelihood of delay, inconsistency, and calculation errors also increases.

TabDeb was developed to solve these issues by digitizing the full debate tournament workflow. The application brings together registration, tournament setup, matchup creation, score processing, ranking, and reporting in one application. It also includes a smart speech workflow that records debate speeches, converts them to text, and generates summaries for easier adjudication and documentation.

The project was originally proposed as a debate management platform with AI features, and the finished application reflects that goal by providing both tournament tabulation tools and speech-processing support.

2. PROBLEM STATEMENT
------------------------------------------------------------
Manual debate tournament management creates several practical problems. Matchups must be generated carefully to ensure fairness. Scores must be recorded accurately and computed consistently. Tournament data must be preserved for later review. Adjudicators also need a reliable way to document speeches and track speaking performance.

Without a centralized system, organizers often rely on multiple documents and manual calculations. This slows down operations and can lead to errors in pairings, ranking updates, and final results. The lack of a unified platform also makes it difficult to manage tournament history, team statistics, speaker statistics, and speech records.

TabDeb addresses these issues by providing a structured digital system that handles tournament lifecycle operations and speech documentation in a single environment.

4. PROJECT SCOPE
------------------------------------------------------------
The scope of TabDeb covers the major operational needs of a debate tournament.

It supports user account creation, login, guest access, and profile management.

It supports tournament creation with metadata such as tournament name, club name, date range, format, location, description, prize pool, and team limit.

It supports team registration, team editing, team removal, and team locking before tournament rounds begin.

It supports roadmap configuration so that the organizer can define the sequence of rounds from preliminary stages to elimination stages.

It supports AI speech recording, transcription, summarization, and PDF export.

It also supports search and profile-based exploration features for users who do not run tournaments.

5. SYSTEM OVERVIEW
------------------------------------------------------------
TabDeb is implemented as a Flutter application connected to Firebase services and a Python backend for the speech pipeline. The overall system is divided into two major operational layers.

The first layer is the tournament management layer, which handles users, tournaments, teams, rounds, matchups, scoring, rankings, and reporting.

The second layer is the AI speech workflow, which handles audio recording, backend job creation, audio upload, transcription polling, summarization, and result export.

These layers are connected through shared authentication and persistent cloud data storage.

The system is designed to be usable on mobile devices and web platforms, and it follows a modular structure so that each major feature can operate independently while still remaining part of one integrated system.

7. PROJECT ARCHITECTURE
------------------------------------------------------------
The application follows a layered and modular architecture.

The model layer contains the domain entities used by the application. These include users, tournaments, tournament segments, teams, debaters, debate matches, speech jobs, and app statistics.

The screen layer contains the user interfaces used for login, registration, dashboard navigation, tournament creation, tournament management, match score submission, summarization, and result presentation.

The service layer handles business logic, data operations, matchup generation, speech API communication, polling, and PDF generation.

The backend layer handles speech job creation, status tracking, transcription, and summarization.

The cloud layer stores authentication data, tournament data, app statistics, speech jobs, and uploaded audio files.

8. CORE MODULES OF THE IMPLEMENTED SYSTEM
------------------------------------------------------------
8.1 Account Management Module

This module handles registration, login, guest access, and profile-related operations.

During registration, users provide details such as name, user ID, email, password, and optional profile information. The application verifies that the selected user ID is unique before creating the account. User records are stored in Firestore, while authentication is handled through Firebase Authentication.

During login, the application first looks up the user ID in Firestore, retrieves the associated email address, and then signs the user in through Firebase Authentication. This approach allows the system to support a username-based login experience while still using email-based authentication in the backend.

Guests can access limited browsing features without full account privileges.

8.2 Dashboard and Navigation Module

The dashboard serves as the central entry point after authentication. It provides quick access to the main features of the application.

Registered users can create tournaments, manage their own tournaments, use the time keeping module, access AI summarization, search tournaments, and search debaters.

Guest users are limited to browsing and search-related functions.

This role-based navigation model keeps the application structured and prevents unauthorized access to tournament management actions.

[Insert Figure 7: Dashboard screenshot here]

8.3 Tournament Creation Module

The tournament creation screen allows organizers to define the main properties of a tournament. These properties include tournament name, club or organizing body, location, description, date range, format, prize pool, and maximum number of teams.

When a tournament is saved, the system creates a unique tournament ID, stores the tournament in Firestore, increments the application statistics, and updates the creator's running-tournament list.

This module forms the entry point for the tournament lifecycle.

[Insert Figure 8: Tournament creation screen screenshot here]

8.4 Tournament Management Module

The tournament management area is one of the most important parts of the application. It loads tournaments that the current user created or co-owns and displays them in a searchable list.

Each tournament can be edited, deleted, viewed in detail, or opened for further operations depending on its state.

The tournament management workflow is state-based. If team addition is still open, the organizer can add or edit teams. If the roadmap is not yet locked, the organizer can configure the sequence of rounds. Once both of these steps are completed, the application can generate matchups for the active segment.

The management module therefore acts as the control center for the tournament lifecycle.

[Insert Figure 9: My Tournaments screen screenshot here]

8.5 Team Management Module

Teams are added with exactly three debaters per team in the implemented workflow. The organizer can create a team, edit team information, or remove a team before locking the tournament registration stage.

When team registration is locked, the application updates the tournament state and records the number of teams and debaters handled by the application statistics module.

This module ensures that tournament membership is properly controlled before rounds begin.

[Insert Figure 10: Add Teams screen screenshot here]

8.6 Roadmap Configuration Module

The roadmap module allows the organizer to define the tournament segment sequence. The application supports standard round names such as preliminary rounds and elimination rounds, as well as custom segments.

Each segment stores information such as its name, segment ID, the number of teams in that segment, the number of auto-qualified teams, and whether it is a tab round or elimination round.

Once the roadmap is saved, it becomes locked so that the tournament structure cannot be changed later.

[Insert Figure 11: Roadmap configuration screen screenshot here]

8.7 Matchup Generation Module

The matchup generation logic creates debate pairings for the current segment. The tournament model contains the actual generation algorithm, which considers tournament stage, team status, prior performance, and side balancing.

In preliminary rounds, teams are paired in a way that supports balanced distribution. In later rounds, the application uses performance-based logic so that stronger teams are paired appropriately.

The system also assigns debate sides, sets venue numbers, and records any auto-qualified teams where applicable.

This module is central to the fairness and efficiency of the tournament system.

8.8 Score Submission and Results Module

After a debate round, adjudicators can submit scores for both teams. The application records individual speaker scores and rebuttal scores, calculates team totals, updates wins and losses, and marks the match as completed.

The score submission workflow also supports editing scores later if corrections are needed.

Because the system updates both match-level data and tournament-level data, rankings stay synchronized across the whole application.

The application keeps track of team ranking, debater ranking, wins, losses, and accumulated scores.

It uses the stored tournament data to show top teams and top debaters after each round or at the end of the tournament.

The application statistics module also tracks platform-level totals such as tournaments created, teams handled, debaters handled, and users registered.

This provides a broader administrative view of system usage.

The time keeping module provides a smart stopwatch-style utility that can support adjudicators during debate sessions.

8.12 AI Speech Processing Module

This module is one of the most advanced parts of the project. It allows the user to record a speech, upload the audio to a backend job pipeline, track transcription status, and generate a summary from the resulting transcript.

The speech workflow begins on the Flutter side when the user records audio. The application then creates a speech job through the backend API, uploads the audio to the signed storage URL, and repeatedly polls the backend until transcription is complete.

Once transcription is finished, the user can open the speech result screen and request summarization. After the summarization process completes, the summary can be viewed and exported to PDF.

This workflow reduces the burden of manual note-taking and improves speech documentation during debate rounds.

9. DATA MODEL SUMMARY
------------------------------------------------------------
The main project entities are User, App, Tournament, TournamentSegment, DebateTeam, Debater, DebateMatch, and SpeechJob.

The User class stores personal account information and the list of tournaments the user runs.

The App class stores global platform statistics such as tournament count and user count.

The Tournament class stores all tournament-related metadata, round information, team lists, debater lists, co-owner information, and lock states.

The TournamentSegment class stores the structure of each tournament round or stage.

The DebateTeam class stores team identity, members, scores, and record information.

The Debater class stores speaker identity and individual performance scores.

The DebateMatch class stores the two teams in a match, their scores, rebuttal marks, completion status, and venue.

The SpeechJob class stores the processing lifecycle of recorded speeches.

10. DATABASE AND STORAGE DESIGN
------------------------------------------------------------
Firestore is used as the main data store for the application.

User documents are stored under the users collection.

Tournament documents are stored under the tournaments collection.

Application-level statistics are stored under the app_statistics collection.

Speech jobs are stored in both a top-level speech_jobs collection and a user-specific subcollection so that both general monitoring and personal access remain efficient.

Uploaded speech audio files are stored in Firebase Storage using a structured path convention based on user ID and job ID.

This design supports both structured retrieval and scalable cloud storage management.

11. IMPLEMENTATION HIGHLIGHTS
------------------------------------------------------------
The project preserves the key logic of debate tournament tabulation while modernizing the user experience through Flutter.

The app supports tournament status-based actions, meaning that users can only perform the operations that are valid for the current state of the tournament.

The matchup system automatically produces round pairings and carries tournament state forward through the segment sequence.

The scoring system updates both match records and tournament-wide records so that rankings remain accurate.

The speech workflow uses a backend job model instead of a single blocking request, which makes transcription and summarization more scalable and easier to monitor.

The implementation also supports co-owner management so that multiple authorized users can work on the same tournament.

13. CHALLENGES AND LIMITATIONS
------------------------------------------------------------
During development, several practical issues had to be addressed.

One challenge was preserving a clear tournament state flow so that users do not skip required steps.

Another challenge was maintaining consistent scoring updates between match-level objects and tournament-level records.

For the speech workflow, the application had to handle asynchronous backend status changes, upload delays, and failure states cleanly.

The current system is already functional, but future versions can improve advanced analytics, reporting flexibility, and tournament visualization.
